# 05｜Notion 双层交付与深度教学正文模板

## A. Step Teaching Note：独立可读的教材

Notion 页面的标题设在属性中，正文不重复同一大标题。只引用最重要的来源页/具体小节，主要说明不应被大量来源表打断。推荐如下组织（是教学函数，不是死板小节数量）：

1. **开篇具体工作问题**：熟悉的主场景、真实输入格式、读者为什么关心、现有朴素方法会出现的困难。教学模拟明确标识。
2. **第一次尝试与失败**：展示初始策略和一个实际可理解的失败情形；解释失败源于什么规则/信息/机制缺口。不能凭空宣称真实模型输出已验证。
3. **核心机制的详细讲解**：按中文直觉 → 正式术语 → 输入、中间过程、判断/反馈、输出 → 反例，穿插必要的简单对照；来源原有高价值解释过程要保留。
4. **改进与权衡**：必要时沿 V0/V1/V2/V3 演化，逐版解释增加了什么、为解决什么问题、会带来什么成本/新风险；非迭代型主题按机制步骤与对照方案组织。
5. **工程实验与验证**：依赖、版本、运行步骤、代码的真实性质；正例、反例、失败分支；若做 A/B，明确测试集、指标和可重复条件。mock、人工构造期望结果和真实 LLM 实测严格区分。
6. **知识边界和简短复习**：何时不适用、与下一个 Step 的分工、一个可复述横向流程、几道自测题以及少量精确的来源链接。

一个主要概念必须被**讲透一次**，但完成“背景/机制/演示/反例”算解释完整，不是冗余。专业名词第一次出现用“中文（English）”，后面使用最自然的叫法。文章以连贯段落为主，不要一句一段、大量标签或无意义表格。没有默认字数上限；用户明确要 review 才将内容收敛成短复习卡。

**案例设计示意（全部是自拟虚构，不是任何公司的真实会议记录）：** 项目周会纪要助手从“帮我总结会议”出发，发现可能把“我建议周五上线”写成已决定；V1 明确只摘确认的结论，V2 用“建议 vs 确认、协助 vs 主责”的对照示例刻画边界，V3 约定 JSON 决策/行动项/待确认字段并在程序中校验。最后用未进入示例的测试集比较，不能只因 Prompt 变长就声称准确率提高。这个例子只适合提示工程等场景；学习 LLM 架构时要选能真正展现 Token/Attention 机制的演示。

## B. Research Record：独立关联页

保存 `source_manifest`、Atomic Claim 与准确小节、`claim_matrix`、独立课程来源组数、主力/补充/独有关系、**关键来源解释链与例子**、版本/冲突/缺口、证据及读者审查、代码验证记录和 `publish_status`。正文引用本记录，但不要把长矩阵追加在课后。

## C. Review Recap：正文最后一小节

五至十条关键结论、几组易混淆概念、横向流程、自测题；须全部在前面正文得到充分解释。不要先写复习提纲再往前堆定义，必须先真正写成适合学习的课程。

## Notion 修改安全

- 用户尚未确认新教学版时，新建候选子页并命名版本，保留原 Step 正文及既有研究/历史页。
- 用户要求覆盖现有 Step 时，先 fetch 并存下可回读完整备份，再使用合法 Notion Markdown 修改，保留所有原生 `<page url="...">` / `<database url="...">` 子内容标签。
- 先验证研究记录，再更新教学正文；发布后重新 fetch 验证主要章节、代码块、来源提及、子页及版本状态。
- 记录 `draft_only` / `created_new` / `updated_existing` / `blocked`；有异步写入或警告应确认结果，不要靠猜测宣称成功。
