# 02｜课程地图驱动的跨课知识综合

先查看用户已有课程地图/Step 覆盖矩阵（若有），确定本节的**主力来源、补充来源、独有价值和知识边界**。按“学习者要解决什么问题”而非“哪门课先讲”聚类，课程数不必平均，重要的独有机制不得因只有一个来源被删除。

每个主题记录：`theme_statement`、Claim IDs、独立来源组、适用条件、`why_needed`（为什么会出现）、`mechanism`（如何运作）、`illustrated_steps`（实际中间变化）、`failure_modes`、`so_what`（实际意义）、`how_to_validate` 与正文落点。这样研究记录不仅能追溯结论，还能支撑**讲解过程**。

六种关系：`SAME`（条件相同的命题）、`COMPLEMENTARY`（机制互补）、`CONFLICT`（同条件下实质冲突）、`UNIQUE`（独有重要内容）、`EVOLVED`（有证据支持的版本演进）、`UNCERTAIN`（不足以核实）。勿因多处重复就认定真理，勿编造冲突；不同框架实现不等同于通用技术原理。

`claim_matrix` 至少包含：Concept｜综合主张｜Claim IDs｜关系｜去相关来源数｜条件/分歧｜正文落点。可扩充“为何需要、原文重要案例和反例”，但只存研究记录，避免正文变成表格汇编。

## v0.3 的融合方法

要融合的是不同课程的**解释力**，而非压缩成几句共识。例如：课程 A 解释为什么提示容易失败，课程 B 解释 Zero/Few-shot 的机制，课程 C 提供 PromptTemplate 代码，课程 D 提醒 Prompt Injection 权限边界。正文应将这些知识按学习过程串起来，而不是四个孤立的“课程要点”。

先画横向依赖链：实际任务 → 朴素方案与问题 → 核心机制 → 输入/过程/输出 → 改进和反例 → 验证/复习。若本主题不是逐版优化型技术（如 Attention 机制），用“输入 → 计算步骤 → 输出”的过程推导替代 V0–V3，禁止为了套模板制造虚假的改进历史。

## 出口验收

不仅能给出综合结论，还能说明哪门课程提供了必要的背景、机制、案例、限制与工程实践；哪些信息待核实；正文没有丢失关键因果关系。
