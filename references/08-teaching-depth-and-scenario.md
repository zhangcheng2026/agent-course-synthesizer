# 08｜v0.3 新增：通用工作场景选择与讲透原理的教学量规

## 目的

将知识综合输出由“结论准确却偏浅”升级为**有过程、有示例、有反例、能复述和能实践**的教材。案例不是装饰：它必须真正承载技术的输入、边界、运行过程及验证。遵循用户选择的教学风格，未指定时优先自然、通俗、跨行业职场情境，而非未经要求的个人职业定制。

## 一、怎样选择一个好案例（先评分后写作）

候选场景优先考虑以下维度，每项逐一判断，不能只凭“听起来有趣”：

| 维度 | 合格标准 | 不合格表现 |
| --- | --- | --- |
| 普遍性 | 多数办公室或 AI 应用工作中可遇到；普通读者不用先学习行业术语 | 需要网络设备命令、医疗术语、复杂财务制度才看懂，用户又未要求 |
| 问题具体 | 有清楚输入、想完成的任务、可检查的输出 | 仅“让 AI 更聪明”“做个智能助手” |
| 可暴露问题 | 朴素方法会在真实有歧义的输入上出错，能解释为什么 | 为了教学硬编不合逻辑的错误或声称实测改善 |
| 可逐步展开 | 可以沿同一案例解释新机制/示例/校验，每步都有因果 | 每节换新场景，读者难以建立整体认知 |
| 可验证 | 可以对输入和预期结果做人工核对、程序校验或 A/B 测试 | 凭“看起来不错”评判效果 |
| 安全准确 | 不用真实客户隐私，不虚构事实和效果；敏感动作交给权限程序 | 把假想模型输出当成真实，或在案例里擅自执行外部操作 |

**推荐候选，依题选取：** 项目周会纪要/行动项；客户咨询分类/工单分派；企业制度文档问答；收件箱摘要与待办；产品需求拆解；报表/数据质量检查。RAG 可用企业制度问答；Prompt 可用会议纪要或工单分类；Tools 可用用户授权的日历/待办更新；Agent Loop 可以用订单状态与后续查询。不应同一个案例生硬套满全部 Step。

**不要因为用户曾从事某行业就默认选该行业**。如果用户明确要求“网络运维专用例子”“医疗背景解释”，则尊重其选择；否则选择普通、易懂的领域并说明为何与本课知识机制吻合。

## 二、深度解释的六个必答问题

对每一个**重要**知识点，作者应能写出下面的答案，不一定呈现为六个标题：

1. **为什么产生？** 先有现实问题而不是定义；读者感到“确实需要”。
2. **简单办法哪里不足？** 给一条合理的输入、朴素处理方式与可观察失败/限制，不虚构模型实测。
3. **它是什么？** 首次术语用简单中文定义，再附英文名，并指出用途。
4. **它怎样一步步工作？** 明确输入、关键中间加工/判断/反馈与输出；每一步说明“为什么这样做”。
5. **新增什么能力、付出什么代价？** 对比方案的优势、失败模式、时间/Token/复杂度/权限限制；不可夸大。
6. **怎么知道做对了？** 用规则检查、对照数据、测试/日志或可运行代码；区分人工示意、mock 与真实模型表现。

核心概念如果只回答“它是什么、有什么好处”，缺少 2/4/6，说明它仍然是复习卡，不是深入教材。

## 三、怎样叙述版本迭代型案例

以**虚构的项目会议纪要提取**说明教学写法（以下非真实会议内容、非原课程实测，不可把它复制成具体课程原作者案例）：

- **V0（任务模糊）**：“帮我总结这段会议。”可能将“我建议周五上线”误写成“会议决定周五上线”，也可能漏掉“主负责人仍待确认”。这里的输出只是可能的错误示意。
- **V1（业务规则）**：说明建议不等于决定、协助不等于主责、未说截止时间不能编造；规定列“决定/行动项/待确认”。解释为什么这些规则解决前面的歧义。
- **V2（边界示例）**：提供“明确决定”“只有建议”“协助但主责未定”三种输入/输出示例。重点解释每个例子的作用和 Few-shot 是上下文引导、不是更新权重；示例数量不是越多越好。
- **V3（结构化结果）**：固定 JSON 字段并由程序独立校验。解析成功、字段类型正确、事实有证据是不同层次；具体 API 的 JSON Schema 支持需核实。
- **比较与验证**：保留一组没有出现在 Few-shot 中的案例，在相同模型/版本/参数下比较字段通过率、决定准确率、负责人臆造次数、Token 成本；未运行时只提供测量计划，不能声称性能提高。

这条链的价值是**每版针对具体问题改变了什么**。其他主题若没有逐版优化的天然过程，不套 V0–V3：例如 Transformer 更适合从 Token→注意力计算→上下文表示→生成解释，RAG 更适合“无资料→检索→引入证据→排序/验证”。

## 四、让专业知识通俗，但不能变成空话

- 将关键术语对照日常动作，解释比喻的边界。例如 Few-shot 像给新员工看几份标准样本，但模型不是人，也没有因此永久学会私有规则。
- 每段围绕一个完整问题，不要一句话独立一段，也不要把七八个技术名词全部扔给初学者。
- 写完“如何工作”之后，必须给一条具体输入走完整个流程；不要用“结果更精准/更稳定”取代证明。
- 原文的关键推导有助理解时，保留或通俗转述，并提供准确归属；自己新增的案例须注明是教学设计。
- 学习正文可以长，但每个段落必须帮助读者形成理解；删冗余时不要删除因果解释和反例。末尾单独写精简复习。

## 五、最终检查清单

- [ ] 案例没有未经用户要求就依赖其个人职业背景；高频且可共情。
- [ ] 真实业务输入/可观察目标/边界清楚，模拟案例有标识。
- [ ] 关键概念能讲清“为什么、怎么做、中间发生什么、何时失效”。
- [ ] 逐步改进的每一步都有对应的失败点；非迭代主题不用硬套版本。
- [ ] 英文术语都有首次中文解释；比喻与实际机制界限清楚。
- [ ] 重要输入、例子、输出一致，不捏造人物、日期、负责人和任务状态。
- [ ] 代码如已运行有客观测试记录；未运行不写“已通过”。
- [ ] 真正的模型 A/B、教学效果、最新 API 能力没有被虚构。
- [ ] 研究矩阵独立保留；正文不是只有总结，结尾有简明复习。
- [ ] 原课程、原稿快照、Notion 子页及来源准确安全。

若任一核心教学项不通过，标 `reader_review=revise`，修正文后才能发布，不可用“知识已经很准确”搪塞解释过程缺失。
