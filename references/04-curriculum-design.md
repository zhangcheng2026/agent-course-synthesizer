# 04｜从知识清单升级为“能学懂的深度课程”

## 一、先确定学习结果，而不是先压缩文章

每个 Step 应让学习者能够：用自己的话解释为什么需要某技术、沿真实输入复述完整工作机制、对比简单与复杂方案、说出适用和失败条件、看懂/运行一个最小例子，并用观察结果检验理解。研究记录保留完整学术信息；正文完成教学任务，不能只贴定义与结论。

**课程地图先行**：用户已有的八门课知识地图决定主力和补充来源；读者所需知识不一定按作者的讲述顺序排列。使用来源最有教学价值的背景、重要推导、例子和反例，不是将它们压缩成“各课总结”。

## 二、先选合适的贯穿案例

阅读 [08-teaching-depth-and-scenario.md](08-teaching-depth-and-scenario.md) 的筛选量规。默认优先跨行业高频、易理解、实际工作中能见到的任务；除非用户指定，不根据读者个人身份选择专业领域。案例需要有真实的输入形式、业务规则、含糊/失败情形、可比较的输出，以及实际可做的验证。每个主案例若为模拟要明确标记为教学模拟。

一个主案例可以在不同环节渐进演变；必要时补一两个短对照，但不要引入大量互不相关、互相干扰的例子。案例的因果关系必须成立，不能为了讲概念假设不存在的结果。不能把一个 Step 2 的 Agent Loop 案例原样强套到 Prompt、LLM、RAG 的教材中。

## 三、强制保留关键解释链，但不机械分标题

核心知识的教学顺序应尽量包含：

1. **问题与背景**：工作中真实发生什么？读者直觉上会怎样处理？
2. **朴素方案与不足**：简单指令、固定流程或已有方法为什么在某个输入/条件下不够？给出具体反例，而非空泛地说“效果不好”。
3. **新技术的机制**：定义首次出现时用日常中文解释，再给中文/英文术语；沿着输入 → 重要中间步骤 → 判断/反馈 → 输出逐一解释“为什么”，必要时作横向流程图。
4. **逐步演化与可观察差异**：每增加规则、示例、组件或一步处理，都解释解决哪一种具体失败；展示输入与期望输出、分支及反例。
5. **工程实践、可检验反馈与边界**：给出能在指定环境使用的最小实现，说明如何运行、正常与异常结果、如何进行对照测试；如未实际运行必须标明。
6. **精炼复习**：压缩为关键区别、流程、适用判断和自测题；不能用这几条反过来代替前面详解。

**场景性迭代**（如 Prompt Engineering）可以写 V0（模糊）→ V1（明确规则）→ V2（代表性 Few-shot）→ V3（结构化输出及校验）→ 测试。每一版必须对应具体要纠正的问题；未做真实模型 A/B 时，只能说“设计演化”，不可说版本性能已经提升。

**机制性主题**（如 Transformer、KV Cache）要用“输入/组成 → 机制步骤 → 结果/复杂度/限制 → 对照反例”，而不是制造没有来源的 V0–V3。**系统架构主题**（如 RAG、Memory）按初始目标、最小流、不同反馈、取舍、失效与验证组织。每节需要的细节由学习目标决定，允许自然变化。

## 四、通俗解释的具体要求

- 先讲“遇到了什么事”，后讲“这个技术叫什么”；首次术语用 `中文（English）`，紧接着说它在场景中做什么。
- 对新的重要术语，用一个短比喻帮助直觉，随后说明“比喻对应实际的哪一部分、哪里不准确”。比喻是脚手架，不是证明。
- 避免同一段连续引入五六个新名词；必要时拆开走流程。
- 多解释“为什么 A 与 B 不同”，例如“Few-shot 的示例在上下文里，不是模型参数更新”“JSON 语法正确，不代表业务事实正确”。
- 理解优先于短小；**不设置 5000–8000 字符目标或正文上限**。有价值的完整推导不删；冗余重复要删。用户偏好笔记紧凑时，可适度合并段落，但不能省略中间环节。
- 主文不以表格堆砌定义；表格用于真正的比较与结构化任务。

## 五、概念边界与前后 Step

开篇说明学习目标和前置知识，结尾指向后续专题。Prompt 的示例设计不等于 Context 的完整历史选择；Tool Call 请求不等于工具真实执行；RAG 检索不等于训练/保证事实；Self-Refine 不等于外部验证。重视框架无关原理；LangChain、HelloAgents 等只是可选实现，不把某框架 API 当普遍定义。

## 六、完成条件

删掉章节末总结后，正文是否仍能让第一次学习的人沿例子解释该技术？是否能讲清一个错误为何发生、为什么采用新方法、怎么证实更好？如果只能背概念，返回补写机制/过程/反例，而不是添加更多术语。
