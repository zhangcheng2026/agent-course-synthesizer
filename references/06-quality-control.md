# 06｜事实审查、教学审查、场景审查与安全发布

## A. 证据审查（硬门槛）

核心主张须有准确来源和章节、前提/版本/研究条件；未读页、附件、实践必须说明；同源副本不重复计独立证据。重要分歧与独有内容不能被“共识”淹没。原作者案例、学员个人笔记、Skill 新编例子区分身份。

任何以下情况直接 `blocked`：核心概念没有可核对的依据；宣称全量阅读却只选了少量页面；假称真 LLM 测试、性能、真人学习反馈；伪造实时产品价格/ API 支持；私有原文或个人数据被复制到公开仓库；擅自覆盖/删除用户的 Notion 内容或子页。

## B. 深度教学审查（v0.3 新增硬门槛）

对于**本 Step 的每个核心技术概念**，审核：

1. 能否从场景中知道**为什么需要**这个技术？不是先看到概念名字。
2. 能否解释**原先更简单的方法在哪种输入/条件下不够**，且具体给出反例？
3. 是否按可理解的顺序展示**输入 → 至少一个重要中间步骤/判断 → 输出/反馈**？不是只有“定义+优点”。
4. 是否阐明**引入该机制究竟改变了什么、又增加了什么限制或成本**？
5. 实践/示例是否解释了**如何验证、无法验证什么**？数值/输出若为模拟必须标明。

若 1–3 缺失于核心概念，即使来源正确也必须 `reader_review=revise`，不能因为文字短而宣称“质量高”。允许教学结构因 Step 不同而变化，不要求所有内容套 V0–V3。

## C. 场景与语言审查（v0.3 新增）

- 默认场景是否**跨行业、工作中高频、容易理解**，或至少符合所学技术的自然使用场景？如果只是为了贴合用户职业而使用专业领域，必须改。用户明确选择了领域则按其要求。
- 有没有真实可识别的输入、具体任务、含糊条件或失败分支、对照输出？人物/日期/责任/证据是否与输入一致？不得为了填满 JSON 字段编造负责人和截止时间。
- 专业词首次出现是否解释作用？比喻是否划定不能等同的部分？阅读时能否跟着过程一步步重建概念？
- 是否用长表格替代了正常讲解？是否把结论当教学正文、把正文当复习卡？
- 对照 A/B、prompt 迭代、模型输出是否真实测试过？“教学预期输出”必须有醒目的性质说明。

## D. 代码/工程可验证性

代码应标注：运行环境、依赖、入口、预期结果、实际是否执行；在可用环境中先运行最小断言，并对错误输入做反例测试。不要把 Python 字符串拼装示例误当成真实 LLM，或把 JSON 语法通过误当事实正确。工具调用须区分模型发请求与程序执行；涉及外部写入、邮件发送、权限和隐私的能力需明确审批和约束。

## E. 安全发布协议（继承 v0.2）

1. 先读 Notion 研究来源、课程地图、目标 Step 与 `notion://docs/notion-flavored-markdown-spec`，确认目标和子页面。
2. 如果只是请用户看候选版，创建独立稿，不静默覆盖。若明确要求大幅替换，创建并回读原稿快照。
3. 建立/核验独立 Research Record 与来源矩阵，保持原始课程只读。
4. 发表教学正文时保留原生子页标签和旧版归档入口；写后 fetch 验证章节、链接、代码、子页没有丢失。
5. 回执列明版本、目的地、覆盖范围、模拟和实测区别，以及 `draft_only / created_new / updated_existing / blocked`。

## F. 质量回归结论

填写 `evidence_review = pass / revise / blocked`、`reader_review = pass / revise / blocked`、`scenario_review = pass / revise / blocked`，每项列出具体修复点。审核是模型编辑模拟，不是有真实学习者参与的实验；任何百分制打分仅可作辅助，不是教学效果实测。
